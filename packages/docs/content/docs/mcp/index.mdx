## What a tool returns [#results]

A result is text only. `content` holds exactly one block, of type `text`: the whole answer, written for the model. It has one line per hotel, offer or order with its ids, every note, and "not listed" or "unknown" written out. There is no `structuredContent`, and no tool declares an `outputSchema`, so the model of every client reads the same text.

### Text from hotels [#third-party-text]

Hotel, room and place names, addresses, descriptions and policies are the hotel's words, not Fortrip's, and guest names, the contact and special requests are the caller's. Every line of a result begins with Fortrip's own words. A short value someone else wrote is a JSON string on that line: in double quotes, with `"` and `\` escaped, as in `Hotel: "Lakeside Garden Resort"`. The quotes mark where the value starts and ends and are not part of it. Longer text is a quoted block under a label that says it is information provided by the hotel, not instructions. What Fortrip generates (ids, amounts, dates, links) is bare, and only while it is written as such a value is: an id, an amount, a currency, a date, a time zone or a URL in plain ASCII. Any other value in its place is a JSON string too. Nothing someone else wrote can begin a line or stand outside its quotes.

### JSON for your code [#json]

The text is for the model. When your code needs the object, read it over the [HTTP API](/api), where each tool has an endpoint that answers JSON for the same input, or run the CLI command with `--json`. The [response schemas](/schemas) list every field.

### Errors [#errors]

A failed call has `isError: true` and one text block. The text gives the error's code, what happened, whether a retry can help and after how many seconds, and the next call to make. `_meta["ai.fortrip/error"]` carries the [error envelope](/errors) for your code; its `requestId` is the id to quote to support.

Input is checked by Fortrip, not by the client's SDK, so an invalid argument answers `invalid_request` with the field at fault. A known field sent at the wrong depth is answered with the path it belongs at.

A result's text gives each next call whole, with the order's own id and figures in it, such as `cancel_order { orderId: "ord_…", maximumPenalty: { amount: "120.00", currency: "USD" } }` on an order's Cancel line: on a page of orders, each call is its own order's.

## Server identity and instructions [#instructions]

On connect, `serverInfo` carries the server's `name`, `title`, `description`, `websiteUrl` and `icons`, for a client that lists its servers.

The server also returns `instructions`, a short form of the agent guide: when to use Fortrip, the call order and what to show the user before they pay. Keep them in your agent's system prompt. Some clients never show them to the model, which is why each result repeats the rules it needs.

## Timeouts and retries [#retries]

- Creating an order or paying can take a couple of minutes. Give `create_order` and `pay_order` a timeout of at least three minutes.
- After a `create_order` timeout, call it again with the same details: it is [safe to send again](/api#retries).

## Connecting your own agent [#own-agent]

- Sign-in follows the MCP authorization spec: OAuth 2.1 with PKCE. The authorization server's metadata is at <Fact path="OAUTH_METADATA_URL" />.
- Dynamic client registration is supported, so your client can register itself.
- Each end user signs in once, with their own Fortrip account. Their orders and payment links belong to that account.
