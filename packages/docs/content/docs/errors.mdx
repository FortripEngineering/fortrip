## Error format [#format]

Every failure answers the same envelope:

```json
{
  "error": {
    "code": "rate_limited",
    "message": "Too many requests; retry later.",
    "retryable": true,
    "retryAfterSeconds": 42,
    "details": { "rateLimit": "search" },
    "requestId": "req_…"
  }
}
```

- `code` is one of the codes below; act on it, not on `message`, which is English for people. A code you don't know: go by the HTTP status and `retryable`.
- `pointer`, when present, is the one field of the request the error is about: a JSON Pointer into the body (`/stay/checkIn`), or `/query/<name>` and `/path/<name>`. Each issue of an `invalid_request` has its own `pointer`.
- `details` is the code's own data, listed with each code below. A code without any has no `details`.
- A retryable error carries `retryAfterSeconds` and the `Retry-After` header.
- `requestId` is the id to quote to support.
- A wrong method answers `invalid_request` with HTTP 405 and an `Allow` header.

### On each surface [#surfaces]

- **HTTP API:** the envelope is the response body, with the code's HTTP status.
- **MCP:** the result has `isError: true` and one text block, which gives the code, what happened and the next call to make. `_meta["ai.fortrip/error"]` carries the envelope. See [MCP errors](/mcp#errors).
- **CLI:** the error goes to stderr, as text or, with `--json`, as the envelope, and the command exits with a code below.

### Acting on a refusal [#refusals]

Three codes answer with what to do instead of only what went wrong:

- `offer_changed` carries the new offer. Show the user every change, and order `details.offer.offerId` if they agree.
- `order_not_cancellable` carries the order's `cancel` as it is now. Its `action` is the mode that applies (`cancel` or `close`), or its `blockedBy` says why neither does. See [Cancel or close](/payments#cancel).
- `payment_total_mismatch` carries the order's `total`. The order hasn't changed: confirm that total with the user and pay again with the same token.

## Rate limits [#rate-limits]

Per account and per minute, shared by the HTTP API, the MCP tools and the CLI. Over a limit, the answer is `429 rate_limited`, and `details.rateLimit` names the limit.

### The offers budget [#offers-budget]

One offers call answers a bounded number of offers, however many hotels it prices, so that a result stays small enough for a model to read. The rule is the same on the HTTP API, the MCP tool and the CLI.

- **Without `limitPerHotel`:** each hotel that has offers gets up to <Fact path="LIMITS.offersPerHotelDefault" />, while the call stays within <Fact path="LIMITS.offersPerCallDefault" /> offers in all. That holds for up to three hotels. With more hotels, the <Fact path="LIMITS.offersPerCallDefault" /> are split evenly among those that have offers: nine each for five hotels, three each for <Fact path="LIMITS.offersHotels" />.
- **With `limitPerHotel`:** each hotel gets up to that many, from 1 to <Fact path="LIMITS.offersPerHotelMax" />, while the call stays within <Fact path="LIMITS.offersPerCallMax" /> offers in all. Past that, the <Fact path="LIMITS.offersPerCallMax" /> are split evenly the same way.
- Hotels with nothing to offer take no share.

The offers a hotel keeps are a spread of choices: the cheapest, the cheapest free to cancel, the cheapest with breakfast, and other rooms, listed cheapest first.

To see more:

- Each hotel's `omitted.byCallLimit` counts the offers a call for that hotel alone would add, and `omitted.byLimit` those a higher `limitPerHotel` or a filter may show. The text of a result says the same per hotel.
- Call again with fewer hotels, or with one hotel and `limitPerHotel` up to <Fact path="LIMITS.offersPerHotelMax" />.
- Narrow the offers with `filters.requireBreakfast` or `filters.requireFreeCancellation`.

An offer that isn't shown still exists: don't tell the user a room or a rate is unavailable because a call didn't list it.
