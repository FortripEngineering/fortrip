The contract, [`@fortrip/agent-contract`](https://www.npmjs.com/package/@fortrip/agent-contract), and the CLI, [`fortrip`](https://www.npmjs.com/package/fortrip), share one version number. Each entry lists breaking changes first, then what is new, then how to migrate. The values in an entry are the ones that release had.

## 5.1.1

Released 2026-11-10.

The schemas keep their shape. The change is to the text that agents read.

### Changed

- `currency` on `search_hotels` and `get_hotel_offers` says when to use `CNY`: when where the agent runs or the conversation shows the user can pay with Alipay, WeChat Pay or a bank card from mainland China, the only ways a CNY order can be paid. The agent tells the user that limit. Chinese text alone is no reason, nor is paying with Alipay or WeChat Pay, which USD orders take too. The Claude plugin's skill and the CLI skill say the same.

## 5.1.0

Released 2026-11-10.

### Changed

- `limitPerHotel` on `get_hotel_offers` (`POST /v1/hotels/offers`) defaults to 15 offers per hotel, up from 10. The maximum is 30, up from 20.

### Migration

- Nothing is required. To keep getting 10 offers per hotel, send `limitPerHotel: 10`.

## 5.0.1

Released 2026-11-09.

The schemas keep their shape. The change is to the text that agents read.

### Changed

- `currency` on `search_hotels` and `get_hotel_offers` says to use `CNY` only for a user who pays with Alipay, WeChat Pay or a bank card from mainland China, the only ways a CNY order can be paid: when the user asks for CNY or says they pay that way. An agent asks only when the conversation suggests it, and otherwise keeps `USD`. The Claude plugin's skill and the CLI skill say the same.

## 5.0.0

Released 2026-11-09.

A major release. A request is priced and charged in one currency, USD or CNY, and `payment.methods` replaces the three payment fields.

### Breaking changes

- `displayCurrency` is now `currency` on `search_hotels` and `get_hotel_offers`. It sets the currency of every price in the answer and of the order made from the offers: a search in CNY gets offers in CNY, and the order is charged in CNY. The default is `USD`.
- `approx` is removed from search hits and offers. Prices are in the request's currency, not converted.
- Money in a request is in the request's or the order's currency, not always USD:
  - `filters.price.maxPerRoomNight` is in the search's `currency`. A different currency is `invalid_request`.
  - `total` on `pay_order` is the order's `price.total`, in its currency.
- `payment.handlers`, `payment.credentialLimits` and `payment.wallets` are removed. `payment.methods` lists what `pay_order` accepts for the order now, one entry per way, by `id`:
  - `payment.handlers` and `payment.credentialLimits` → the `stripe_shared_payment_token` entry, with `handler` and `limits { maxAmount, currency, expiresAt }`. The entry is absent where `handlers` was `[]`.
  - `payment.wallets` → the `stripe_alipay_wechat_pay` entry, with `open`, `current`, `wechatPay` and `alipay`. The entry is absent where `wallets` was `null`.
  - `[]` means: give the user `payment.url`.
- `pay_order`'s `method: "alipay_wechat_pay"` is now `method: "stripe_alipay_wechat_pay"`. A token is sent as before.
- `maximumPenalty` on `cancel_order` is Money, the order's `cancel.penalty` exactly as returned, in whatever currency it is, instead of a JSON number. It is optional: an unpaid order is closed without it.
- `get_planning_guide` is removed, and so is `fortrip guide`. The planning guide is a file in the Claude plugin and the CLI skill, `references/planning.md`.
- One offer is one order. Ordering the same offer again answers its order: the same details replay it, and other details answer `offer_already_ordered`, even when that order failed or expired. Another order of the stay, for another party or after an order failed or expired, takes a new offer and gets its own `orderId`. Nothing refuses a second open order of the same stay any more: when a new order replaces an unpaid one, have the user pay only the new link, or close the old order with `cancel_order`. The errors `order_exists`, `order_removed` and `order_attempts_exhausted` are removed: the server no longer answers them.
- CLI:
  - `--display-currency` is now `--currency`, and `FORTRIP_DISPLAY_CURRENCY` is now `FORTRIP_CURRENCY`.
  - `orders pay --wallet` is now `--method stripe_alipay_wechat_pay`.
  - `orders cancel --max-penalty` takes the amount as before, e.g. `12.50`; the CLI now reads the order for the currency, that of the order's `cancel.penalty`, else of its `price.total`. `orders pay --total` is likewise in the order's currency.
  - `--price-max-per-room-night` is in the search's `--currency`.

### New

- `cancel_order` closes an unpaid order. Such an order has `cancel.available` `true` with `cancel.reason` `unpaid`; `cancel_order` with the `orderId` alone makes it `expired`, and nothing is charged. A paid order is cancelled as before, with `maximumPenalty`.
- `orders cancel --close` closes an unpaid order. Exit codes:
  - 0: the order is closed, or was already `expired`.
  - 1: the order can't be closed, or was paid meanwhile.
  - 2: the order is paid (cancel it with `--max-penalty`), or `--close` is given with `--max-penalty`.
- `orders cancel --max-penalty` on an unpaid order cancels nothing and exits 2, as `orders cancel` with neither option does.
- `expired` also means an order that was closed.
- The error `currency_unavailable` (422), with `details { currency }`: prices in that currency aren't available. Offer the user USD.
- `payment.url` is `null` for an order awaiting payment only while its payment is `unpaid` and the link couldn't be read this time; read the order again. A held payment (`payment.status` `authorized`) has no link: the link stops working once a payment succeeds.
- The user pays on `payment.url`, a Fortrip page that continues to the payment provider: Stripe for a USD order, a cashier in China (Alipay, WeChat Pay or a Chinese bank card) for a CNY order. Or they pay by a way listed in `payment.methods`.
- A CNY order is charged in CNY: `payment.localCurrencyAtCheckout` is `false`, `payment.localCharge` is `null`, and `payment.methods` is empty, so it is paid only through `payment.url`. A token is charged in USD, and the cashier takes Alipay, WeChat Pay and Chinese bank cards itself.
- With `fortrip guide` gone, nothing pins the CLI version any more: the CLI skill runs `npx -y fortrip@latest`, as before.

### Migration

- Send `currency` instead of `displayCurrency`, and read every price in that currency without converting it. `approx` is gone.
- Send `filters.price.maxPerRoomNight` and `total` as Money in the search's and the order's currency.
- Send `maximumPenalty` as Money, the order's `cancel.penalty` exactly as returned.
- Read `payment.methods` instead of `payment.handlers`, `payment.credentialLimits` and `payment.wallets`, and send `method: "stripe_alipay_wechat_pay"` to open an Alipay or WeChat Pay payment.
- Handle `currency_unavailable`.
- `cancel.available` is also true for an unpaid order (`reason` `unpaid`, `penalty` null): check `reason`.
- Close an unpaid order with `cancel_order` when the user no longer wants it.
- Stop calling `get_planning_guide` and `fortrip guide`.
- Drop any handling of `order_exists`, `order_removed` and `order_attempts_exhausted`. To order a stay again, get offers again and order the new offer; when it replaces an unpaid order, close that one or tell the user to pay only the new link.
- Update the CLI to 5.0.0, and use `--currency`, `FORTRIP_CURRENCY` and `--method`. A 4.x CLI shows this server's searches, offers and orders only as raw JSON, and its cancel, Alipay or WeChat Pay and `--display-currency` requests are refused, as is its token payment of a CNY order.

### Package

- `usdMoney` is now `requestMoney(name)`: Money in USD or CNY, whose refusal names the field.
- `DISPLAY_CURRENCIES` is now `CURRENCIES`, with the type `Currency`.
- New: `PAYMENT_METHOD_IDS`, `paymentMethod`, and the types `PaymentMethod` and `PaymentMethodId`.
- The `PAY_WAYS` values are `payment_link`, `stripe_shared_payment_token` and `stripe_alipay_wechat_pay`.
- `RenderedTool` and `HttpToolName` are every tool name, `get_planning_guide` being removed.
- `UNKNOWN_IS_NOT_NO_EXEMPTIONS` keys `payment.handlers` and `payment.wallets.open` are now `payment.methods` and `payment.methods.open`.
- `LIMITS.ordersPerStay` is removed, and so are the three error codes, from `ErrorCode`, `ERROR_CODES` and `ERROR_DETAILS`.
- A Money a request sends (`requestMoney`, and `cancel_order`'s `maximumPenalty`) is typed as `Money` on input too: `CancelOrderInput`, `PayOrderInput` and `SearchHotelsInput` no longer have `unknown` for it.
- `ToolSpec.input` and `ToolSpec.output` are required, not `null`. `PositionalSpec.field` is a `string`, and `PositionalSpec.optional` and `FlagSpec.optional` are removed. The `guide` command is removed from `COMMANDS`.

## 4.3.1

Released 2026-11-06.

The schemas keep their shape. The changes are to the text that agents and users read.

### Changed

- Response fields that were undescribed now say what they mean, in the MCP tools' output schemas and the OpenAPI document:
  - offers: `confirmation`, `price.perNightAllRooms`, `cancellation.asOf`, the meals' `unspecifiedMainMeals` and `guestsCoveredPerRoom`, `payAtProperty`, every `omitted` count, and each `unavailable[].reason`;
  - orders: `status`, `price.total`, the item's `cancellation` and `payAtProperty`, and `payment.expiresAt`, `chargeCurrency`, `localCurrencyAtCheckout` and `localCharge`;
  - search: every `coverage` count.
- `payment.handlers` also lists an open Alipay or WeChat Pay payment among the reasons it can be empty.
- `maximumPenalty` is described as a JSON number equal to the order's `cancel.penalty.amount`, e.g. `120.5` for `"120.50"`.
- Tool titles are the operation names the docs use: Planning guide, Hotel details, Live offers, Create order and Pay order. The other tools' titles are unchanged.
- Descriptions and texts call a locality a locality, not a hub. The `hub` field keeps its name.
- CLI:
  - `orders cancel` shows `--max-penalty` as optional: without it, the command shows the penalty and refund and cancels nothing.
  - `orders pay --token` says it is for agents that can request a token from the user's Link wallet, and `orders pay` calls that token a Link token.

## 4.3.0

Released 2026-11-05.

No change to the API, the MCP tools or the CLI.

### Package

- The contract exports more of the values these docs state, so a client can read them instead of copying them:
  - `HTTP_ROUTES` and `ACCOUNT_ROUTES`: each endpoint's method and path. `routePath()` builds a request path from an input.
  - `RATE_LIMITS`: the requests a token may make per scope and window.
  - `ENABLED_REGIONS`, from the new entry point `@fortrip/agent-contract/regions`: the regions a search can be scoped to.
  - `PAY_WAYS` and `PAY_INPUT_WAYS`: the ways an order is paid, and the way each field of the `pay_order` input pays by.
  - `LIMITS` gains `tokenPaymentMaxUsd`, `payMinMinutesLeft` (the time that must be left to pay for a token or wallet payment to be offered), `payCutoffMinutes` (the time left below which `pay_order` refuses), `tokensPerOrder`, `wechatCodeMinutes` and `ordersPerStay` (the orders one stay can have).
  - `SUPPLIER_OUTCOME_STATUS`: the HTTP status of `supplier_unavailable` for each `details.outcome`.
  - `SEARCH_RULES`, `ORDER_HTTP`, `ME_SCOPES`, `MCP_SERVER_URL`, `SKILL_INSTALL_COMMAND`, `REPOSITORY_URL` and `DOCS_ORIGIN`.

## 4.2.0

Released 2026-11-04.

### New

- Pay an order with Alipay or WeChat Pay. `pay_order` (`POST /v1/orders/{orderId}/pay`) takes `method: "alipay_wechat_pay"` with the order's `total`. The answer is the order, with a WeChat Pay code and an Alipay link in `payment.wallets`. The user pays once, by either. Both charge at once.
- `order.payment.wallets` is always sent: `{ open, current, wechatPay, alipay }`, or `null` when the order can't be paid this way and no wallet payment is open. `wechatPay.qrData` and `wechatPay.qrImageUrl` are `null` when there is no live code. A WeChat Pay code lasts 120 minutes.
- The text of `book_hotel`, `get_order` and `list_orders` results has a consent paragraph for an order that offers Alipay or WeChat Pay.
- CLI: `fortrip orders pay <orderId> --wallet --total <total>` prints both links, and draws the WeChat Pay code in a wide enough terminal.

### Changed

- `limitPerHotel` on `get_hotel_offers` (`POST /v1/hotels/offers`) defaults to 10 offers per hotel, up from 5. The maximum is still 20.
- An order's `payment.url` is a Fortrip page, for paying and, after payment, for the order's status.

### Migration

- Nothing is required. To keep getting 5 offers per hotel, send `limitPerHotel: 5`.

### Package

- The contract exports the Alipay or WeChat Pay consent paragraph as `WALLET_NEXT_STEP` and `walletNextStep`.

## 4.1.0

Released 2026-11-04.

The schemas keep their shape. Most changes are to the text that agents and users read.

### Changed

- Paying by token: use a token only with a tool that can request one from the user's Link wallet; otherwise give `payment.url` and never ask for a token. Pay one way only. The charge is in USD.
- `payment_total_changed` asks the agent to confirm the order's total, then retry with it and the same token.
- Field descriptions are corrected or added:
  - `payment.credentialLimits`: the token must allow at least `maxAmount` and stay valid until at least `expiresAt`.
  - `payment.handlers` lists every reason it can be empty.
  - `payment.url` depends on `requiresSignIn`.
  - `checkOut` states the range: 1 to 15 nights, `stay_unsupported` (`max_nights`) beyond 15, `invalid_request` past 30. Validation is the same as in 4.0.0.
- An order awaiting payment says it doesn't need cancelling: it expires unpaid.
- API error messages no longer name MCP tools.
- CLI: the text of results and errors names CLI commands and flags instead of MCP tools.

### Migration

- Nothing is required. A 4.0 or 4.1 CLI works with either server.

### Package

- `renderToolResult` and `renderError` take an optional surface, `"mcp"` by default. With `"cli"`, the text names CLI commands and flags instead of tools.

## 4.0.0

Released 2026-11-04.

A major release. It removes what was kept for older clients, and makes required what the server always sends.

### Breaking changes

- `payment.handlers[].networkId` is removed. `schema`, `available_instruments` and `config { environment, business_profile }` are required.
- `payment.handlers` is always sent: `[]` when a token can't pay the order, with `payment.credentialLimits` `null`.
- `order.cancel` is always sent.
- A hotel's `photos` and a search hit's `photo` are always sent, `null` when there are none.
- Each error code's `details` is required where the code defines it. `search_too_broad`'s `details.center` is required and may be `null`.
- No token payment over $500, Link's cap per spend request. Such an order has empty `payment.handlers`, and `pay_order` answers `payment_method_unavailable` before anything is charged. Exactly $500 can still be paid by token.
- The API takes only an OAuth bearer token as the caller's identity. OAuth authorization-server metadata is served on `mcp.fortrip.ai` only.
- CLI:
  - With `--json`, a 429 without Fortrip's error envelope is reported as `service_unavailable`, retryable, instead of `rate_limited`. The exit code is still 4.
  - With `--json`, a local `invalid_request` always carries `details.issues`, empty for an error in the command line itself.

### New

- The hosted API and MCP server take the 3.5.0 additions: UCP's handler fields, and the token in `payment.instruments`.

### Migration

- Request the token with `config.business_profile` in place of `networkId`.
- Treat an empty `payment.handlers` as "no token payment", instead of checking whether the field is present.
- Update the CLI to 4.0.0. A 3.x CLI can't read the orders this server sends.

### Package

- `strictErrorEnvelope()` is removed: use `strictOutput(errorEnvelope)`.

## 3.5.0

Released 2026-11-04.

### New

- `payment.handlers[]` gains UCP's handler fields, in UCP's snake case: `schema`, `available_instruments` and `config { environment, business_profile }`.
- `pay_order` also takes the token in UCP's Complete Checkout form, `payment.instruments`. The selected instrument must be a `stripe_payments` card with a `stripe_payment_token` credential. A card number anywhere in the instruments is refused.
- Agents are told to request the token with `config.business_profile`.

### Deprecated

- `networkId`, equal to `config.business_profile`. It is removed in 4.0.0.

### Package

- `sharedPaymentTokenOf(input)` returns the token from either form.

## 3.4.0

Released 2026-11-03.

### New

- Pay an order with a Stripe shared payment token from the user's Link wallet: `pay_order`, `POST /v1/orders/{orderId}/pay`, with `sharedPaymentToken` and the order's `total`. The answer is the order, `confirming`, with its payment `authorized`: the amount is held, and charged once the hotel confirms.
  - A token pays one order only. Calling again with the same token answers what the first call answered and never charges twice.
  - Once `pay_order` succeeds, `payment.url` stops working. A payment that fails leaves the link open.
- `payment.handlers` and `payment.credentialLimits` (`maxAmount` in cents, `currency`, `expiresAt`) appear on an order a token can pay: awaiting payment by link, in USD, with at least 15 minutes left to pay. A handler is `{ id, type, version, spec, networkId }`, and agents request the token with the handler's `networkId`.
- New error codes: `payment_total_changed`, `order_not_payable`, `payment_in_progress`, `payment_credential_invalid`, `payment_declined`, `payment_action_required` and `payment_method_unavailable`. New rate-limit scope: `orders_pay`.
- The rule for paying by token is in `pay_order`'s description, and in the text of results that hold an order a token can pay. It never goes in `nextStep`.
- CLI: `fortrip orders pay <orderId> --token <token> --total <total>`.

### Package

- `PAY_NEXT_STEP` is the rule for paying by token.

## 3.3.1

Released 2026-11-03.

### Changed

- A stay can be ordered again once its order is confirmed, cancelled or refused by the hotel. A party with none of an open order's guests gets an order of its own. `order_exists` now answers only:
  - an open order that shares a guest with the request, names compared in any letter case;
  - an earlier order that failed at the hotel with its outcome unknown;
  - a stay that has had 20 orders.
- Another order of a stay needs a new offer, since an offer is ordered once (`offer_already_ordered`). When the new order replaces an unpaid one, the user pays only the new link; the earlier one expires unpaid.
- The contract's wording changes to match. No schema change.

## 3.3.0

Released 2026-10-27.

### New

- Cancel an order under its terms: `cancel_order`, `POST /v1/orders/{orderId}/cancel`, with `maximumPenalty`. The answer is the order: `cancelling`, then `cancelled`. If the hotel refuses, the order is `confirmed` again with `cancel.reason` `refused`.
- `order.cancel`: `{ available, reason, penalty, refund }`. `penalty` and `refund` are in the charge currency. `reason` is one of `CANCEL_REASONS`.
- New error codes: `cancellation_changed`, when the penalty is now above `maximumPenalty`, and `order_not_cancellable`, with `details.reason`. New rate-limit scope: `orders_cancel`.
- The consent rule for cancelling is in `cancel_order`'s description, and ends the text of `get_order` and `list_orders` results that hold a cancellable order. It never goes in `nextStep`.
- CLI: `fortrip orders cancel <orderId> --max-penalty <amount>`. Without `--max-penalty` it cancels nothing: it prints the order's penalty and exits with code 2.

### Package

- `CANCEL_NEXT_STEP` is the consent rule for cancelling.

## 3.2.0

Released 2026-10-27.

### Changed

- `get_hotel_offers` returns a spread of choices instead of the cheapest few. Up to `limitPerHotel` offers are picked in this order: the cheapest, the cheapest that can be cancelled free, the cheapest with breakfast, the cheapest of each other room, then the rest by price. They are listed cheapest first.
- Offers a caller couldn't tell apart collapse into one. `omitted.dominated` counts them too.
- No schema change.

## 3.1.0

Released 2026-10-26.

### New

- Hotel photos, on Fortrip's own URLs. A search hit's `photo` is the hotel's cover. A hotel's `photos` lists up to 8, cover first, and is `null` when there are none.
- The MCP results of `search_hotels`, `get_hotel` and `get_hotel_offers` end with a hint on how to present hotels.
- The text of a search shows each hotel's cover URL, and the text of a hotel its first 4 photo URLs.

### Package

- The presentation hint is exported as `PRESENTATION_HINT`.

## 3.0.0

Released 2026-10-25.

The first release of Fortrip API v1. This changelog starts here.

- The HTTP API on `https://api.fortrip.ai`: search hotels, read a hotel, get live offers, order an offer, and read and list orders.
- The MCP server on `https://mcp.fortrip.ai`, with the tools `get_planning_guide`, `search_hotels`, `get_hotel`, `get_hotel_offers`, `book_hotel`, `get_order` and `list_orders`.
- The CLI, `fortrip`: hotel and order commands, sign-in, the guide, and `fortrip mcp`, a local bridge to the MCP server. Text output by default, `--json` for one line of JSON, and exit codes 0 to 4.
- Ids are opaque, with the prefixes `htl_`, `off_` and `ord_`.

### Package

- The contract, `@fortrip/agent-contract`: the input and output schemas, error codes, limits, the tool and command specs, and the text renderers `renderToolResult`, `renderError` and `renderGuide`.
